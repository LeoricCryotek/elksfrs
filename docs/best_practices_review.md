# FRS best practices review

Reviewed November 2, 2026. Resulting module version: **19.0.3.0.2**.

This review covered the QuickBooks connector, API permissions, OAuth identity,
posting and reconciliation, budget approval transitions, generated report HTML,
installation order, and legacy migration behavior. It is a code and regression
review, not a certification of local bylaws, bookkeeping completeness, or every
cash-management/import path in the module.

## Findings corrected

| Priority | Finding | Correction |
| --- | --- | --- |
| P1 | New installations failed because child menus referenced Accounting before its external ID existed. Existing databases concealed this. | Define the Accounting menu before its children; confirmed by a real fresh Odoo installation. |
| P1 | UI-readonly source fields could be written through RPC by an FRS manager, including source payloads, amounts, source-change flags and journal links. | Public create/write reject imported provenance and accounting-status changes. The private importer retains ordinary ACL checks and does not grant sudo rights. |
| P1 | Managers could repoint a connection's realm or alter OAuth status through RPC. | Connection identity, authorization status and credentials require system-administrator privileges. |
| P1 | An HTTP 200 response containing a Fault, missing QueryResponse or invalid records could be treated as an empty purchase result and mark valid expenses missing. | Validate the response envelope and records before yielding results; failure leaves missing-record inference and the successful-sync timestamp untouched. |
| P1 | After reconciliation, users could edit/cancel an FRS entry or alter/delete its lines while the charge still appeared recorded. | Lock linked journals and financial line fields against modification. Require audited adjustments; reports also reject unposted or unbalanced linked entries. |
| P1 | Budget approval methods could skip steps over RPC. Only initial submission checked for a budgeted loss. | Validate state transitions in ORM create/write and revalidate the budget at approval/submission steps. |
| P1 | A transfer could reference lines in different budgets despite the form dropdown domain. | Enforce the same-budget condition on the server. |
| P2 | Purchase approval and line values could remain cached from before a lock was acquired. Budget account lock order was nondeterministic. | Flush pending data, lock then invalidate/read PO data; lock budget accounts in stable ID order. Check ORM access before locking connector records. |
| P2 | A concurrent sync exposed a raw PostgreSQL lock error. | Translate lock contention inside a savepoint into a user-facing retry message. |
| P2 | Recording any charge froze every account mapping, including newly discovered accounts. | Freeze only mappings actually referenced by recorded charges. Preserve vendor mappings once matched/recorded. |
| P2 | Account/department names were interpolated into unsanitized report HTML. | Escape dynamic labels while retaining the report's authored markup. |
| P3 | Compiled bytecode was tracked in Git despite ignore rules. | Remove tracked generated bytecode; Python can regenerate it for the server's interpreter. |

The fixes reuse the existing models, tables and external IDs. They do not copy
transactions, post financial entries, reinterpret account mappings, reset cron
settings, or change production database data as part of the review. No additional
data migration is needed for these code guards; the existing legacy adoption
migration remains in place.

## Verification performed

Tests used isolated databases, separate temporary data directories, no scheduled
jobs and a separate test port. The working Odoo database was not upgraded.

- Real Odoo installation with FRS and Elks Purchase Requests succeeded after the
  menu-order fix.
- Real Odoo upgrade with both modules: 22 test cases, zero failures/errors; the
  case explicitly for missing Purchase Requests was skipped as expected.
- Real FRS-only installation: zero failures/errors; tests requiring the optional
  Purchase Requests module were skipped as expected.
- Full posting regression: approved budget, Board/Floor-approved PO, dummy test
  signatures, one balanced FRS entry, idempotent second recording and immutable
  reconciled journal.
- Security regressions cover forged charges/status fields, unauthorized realm
  changes, malformed API results, new-account mapping after first posting,
  cross-budget transfers and HTML escaping.
- Fifteen PostgreSQL migration tests passed, including repeat adoption,
  ownership transfer, conflict checks and legacy-placeholder removal hooks.
- Twelve standalone payload tests and two tests of the real Odoo CSV importer
  passed.
- Python/XML parsing and Git whitespace checks passed.

## Remaining limits and follow-up work

1. **Bookkeeping coverage:** this remains a Purchase-expense connector, not a full
   QuickBooks general-ledger mirror. Bills/BillPayments, refunds, payroll,
   partial/combined payments, transaction tax, multicurrency and pending bank feeds
   require their documented separate accounting paths. Do not infer complete FRS
   financials from a successful expense pull.
2. **Purchasing policy:** the application records approval states/signatures, but
   the base budget workflow has no vote-count fields or mathematical enforcement
   of a two-thirds vote and no separate Board/Floor permission groups. Local
   purchasing authority and vote evidence still require review. Transition guards
   enforce order, not that a real vote occurred.
3. **Corrections:** changes to an already matched/posted source remain blocked for
   treasurer review. There is no supported automatic reversal/correction wizard.
   Journal immutability deliberately prevents editing reconciled history to work
   around this.
4. **Shared base ledger:** FRS accounts, budgets and journals still lack full
   company isolation. QBO posting remains restricted to single-company databases;
   this review does not make the entire FRS module multi-company safe.
5. **Base-ledger audit controls:** the new immutable-entry guard covers entries
   linked to QBO. Manual FRS journals, reopening approved budgets, edits to budget
   lines and amendment/transfer concurrency need a broader ledger-locking and
   permissions design before claiming a comprehensive audit trail.
6. **Live Intuit operation:** network calls were mocked for these regressions.
   Actual authorization, token expiry/revocation, rate limits, large histories and
   source corrections must still be exercised against an Intuit sandbox.
7. **Operational scale:** pulls still query the full configured date range in a
   single transaction and rely on a later scheduled/manual retry after an HTTP
   failure. Bounded jobs, backoff and a durable run/error log are recommended before
   increasing transaction volume substantially.

Deploy and upgrade FRS using the existing installation guide after reviewing
these limits. These changes have not been applied to the running Odoo database.
